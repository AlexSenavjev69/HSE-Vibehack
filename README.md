# Добрые дела

Мобильное приложение на React + Vite. Профили, заявки, отклики и рейтинги хранятся в Appwrite.

## Локальный запуск

```bash
npm install
npm run dev
```

Откройте адрес Vite на `localhost`. В `.env` уже предусмотрены:

```dotenv
VITE_APPWRITE_ENDPOINT=https://your-appwrite.example/v1
VITE_APPWRITE_PROJECT_ID=your-project-id
VITE_APPWRITE_DATABASE_ID=your-database-id
VITE_APPWRITE_USERS_TABLE_ID=your-users-table-id
VITE_APPWRITE_CITIES_TABLE_ID=your-cities-table-id
VITE_APPWRITE_REQUESTS_TABLE_ID=your-requests-table-id
VITE_APPWRITE_REQUESTS_ANSWERS_TABLE_ID=your-answers-table-id
VITE_APPWRITE_REVIEWS_TABLE_ID=your-reviews-table-id

VITE_USE_TEST_TELEGRAM_ID=true
VITE_TEST_TELEGRAM_ID=100000001
VITE_APPWRITE_PROFILE_FUNCTION_ID=

APPWRITE_API_KEY=
APPWRITE_CITIES_NAME_COLUMN=cityName
TELEGRAM_BOT_TOKEN=
```

Заполните реальные ID и `APPWRITE_API_KEY` со scopes `rows.read` и `rows.write`.
API-ключ читает только сервер Vite; у него **не должно быть префикса `VITE_`**.
Не публикуйте ключ в клиентском коде. `.env` исключён из Git; шаблон — `.env.example`.
После изменения `.env` перезапустите Vite.

При `VITE_USE_TEST_TELEGRAM_ID=true` вход использует тестовый ID. Этот режим работает
только в разработке на localhost, с пустым `VITE_APPWRITE_PROFILE_FUNCTION_ID`.
Чтобы проверить другого пользователя, поменяйте тестовый ID и перезапустите сервер.
Локальный API не принимает запросы из сети или через публичный туннель.

При `VITE_USE_TEST_TELEGRAM_ID=false` приложение ждёт подписанные данные
`Telegram.WebApp.initData`. Если открыть его обычным браузером без Telegram,
появится сообщение об отсутствии данных входа; тестовый ID автоматически не подставляется.
В production тестовый режим отключён независимо от значения флага.

## Таблицы Appwrite 1.9.6

В Users используются точные ключи колонок:

| Колонка | Тип / содержимое |
| --- | --- |
| `tgId` | text, Telegram ID как строка; уникальный индекс |
| `name`, `surname`, `phone` | text |
| `tags` | массив text (в консоли отображается `tags[]`) |
| `isProfileCompleted` | boolean, исходно false |
| `groups` | many-to-many, при регистрации пустой массив; заполнение необязательно |
| `cities` | many-to-one к Cities, одна запись города; допускает null для черновика |
| `time`, `district` | text, свободный ввод |
| `Rating` | double, средняя оценка по отзывам, 0 при отсутствии отзывов |

В вашей таблице Cities текстовая колонка называется `cityName`. Её ключ задаётся
серверной переменной `APPWRITE_CITIES_NAME_COLUMN=cityName`; для другой схемы
можно указать `name`. На эту колонку нужен уникальный индекс.
Название города приводится к нижнему регистру, все пробельные символы удаляются:
`Нижний Новгород` → `нижнийновгород`. Дефисы сохраняются.
Сначала выполняется поиск по `Cities.cityName`; существующая запись переиспользуется,
иначе создаётся новая. Её `$id` записывается в `Users.cities`.
Для старых городов заранее приведите `cityName` к тому же формату.

Колонки профиля должны допускать пустые значения при создании черновика;
связь `cities` должна быть необязательной на уровне схемы. Другие обязательные
колонки с отсутствующими значениями помешают создать пустого пользователя или город.
Сервер требует заполнить имя, фамилию, телефон, минимум один навык, город, район
и время перед установкой `isProfileCompleted=true`. `groups` не участвует в проверке
и не изменяется при редактировании профиля. Позже названия групп можно читать из `Groups.name`.

Users и Cities не требуют публичных разрешений на чтение или изменение.
Серверный обработчик получает доступ через API-ключ, клиент работает только со своим профилем.
Не выдавайте `Any` права на таблицу Users: там хранятся телефоны.
Web-платформа Appwrite должна содержать hostname сайта и localhost для разработки.

## Запуск из Telegram

Для размещённого сайта нужен сервер, который проверяет подпись Telegram.
Готовый обработчик находится в `server/profile-api/` и разворачивается как Appwrite Function:

1. Создайте Function с Node.js 22+; загрузите содержимое `server/profile-api/`
   как корень функции. Entry point: `main.js`, зависимостей нет, таймаут — 60 секунд.
2. Разрешите выполнение функции роли `Any`. Каждое обращение внутри функции
   проверяет подпись Telegram; доступ к таблицам остаётся закрытым.
3. В настройках динамического ключа функции включите `rows.read` и `rows.write`.
   Ключ Appwrite передаётся серверу в `x-appwrite-key`; в сборку React он не попадает.
4. Задайте **в окружении функции** `TELEGRAM_BOT_TOKEN`, `APPWRITE_DATABASE_ID`,
   `APPWRITE_USERS_TABLE_ID`, `APPWRITE_CITIES_TABLE_ID`, `APPWRITE_REQUESTS_TABLE_ID`,
   `APPWRITE_REQUESTS_ANSWERS_TABLE_ID`, `APPWRITE_REVIEWS_TABLE_ID`,
   `APPWRITE_CITIES_NAME_COLUMN=cityName`.
   Endpoint и Project ID функция получает из стандартных
   `APPWRITE_FUNCTION_API_ENDPOINT` / `APPWRITE_FUNCTION_PROJECT_ID`.
5. В `.env` React задайте `VITE_USE_TEST_TELEGRAM_ID=false` и
   `VITE_APPWRITE_PROFILE_FUNCTION_ID=<ID функции>`, затем выполните `npm run build`.
6. Разместите `dist` на HTTPS-домене, добавьте этот hostname как Web-платформу Appwrite
   и укажите адрес Mini App в настройках Telegram-бота.

`npm run preview` обслуживает production-сборку: для неё требуется функция,
локальный тестовый обработчик там не запускается.

Telegram SDK загружается только в Telegram-режиме. Сервер проверяет HMAC-подпись,
`auth_date` (не старше часа) и ID из подписанных данных; произвольный tgId из браузера
в production не принимается. Если вход устарел, приложение нужно открыть заново.
Подробности: [Telegram: проверка initData](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app),
[Appwrite Functions](https://appwrite.io/docs/products/functions/develop).

## Сценарий профиля

При каждом запуске приложение запрашивает Users по `tgId`. Если пользователя нет,
создаётся запись с пустыми полями и `isProfileCompleted=false`.
До успешного заполнения профиля ни один экран приложения и нижняя навигация не доступны,
включая переход по прямому hash-адресу. Ошибка API также не открывает доступ.
Форма состоит из трёх шагов: контакты, навыки, город/район/время.
Данные формы и флаг сохраняются одним обновлением Users после получения ID города;
только подтверждённое сервером сохранение открывает приложение.

Существующие группы при сохранении не изменяются. Повторные запросы и одновременные
запуски используют одну запись пользователя/города; дополнительно нужны уникальные индексы.
Если у старого профиля флаг true, но нет новых обязательных полей, форма попросит их заполнить.
Редактирование профиля использует тот же сервер и те же правила.

## Структура и экраны

- `src/pages/onboarding/` — проверка входа, состояния загрузки/ошибки, обязательное заполнение.
- `src/pages/profile/` — профиль и общая форма заполнения/редактирования (JSX + SCSS).
- `src/pages/home/`, `create-request/`, `activity/`, `requests/` — лента, создание, списки и подробности заявок.
- `src/lib/` — Appwrite Web SDK 26.2.0, Telegram и вызов API профиля.
- `server/profile-api/` — проверка Telegram, валидация, Users/Cities и entry point функции.
- `server/vite-profile-api.js` — локальный API для разработки.

Маршруты: `#/`, `#/create`, `#/profile`, `#/profile/edit`, `#/profile/requests`,
`#/profile/responses`, `#/requests/:id`. После регистрации открывается главная.

## Заявки

Форма сохраняет запись в Requests через тот же серверный API (Appwrite Function
для размещённого сайта, Vite API для localhost). В окружении функции добавьте
`APPWRITE_REQUESTS_TABLE_ID`; локально используется `VITE_APPWRITE_REQUESTS_TABLE_ID`.
После обновления кода повторно разверните функцию, чтобы появились действия
`requests.list` и `requests.create`.

| Поле формы | Колонка Requests |
| --- | --- |
| Название заявки | `name` |
| Что нужно сделать | `description` |
| Категория и отметки «Срочно» / «Онлайн» | `tags`, массив строк; отметки `срочно`, `онлайн` |
| Что вы готовы сделать взамен | `reward`, необязательно |
| Автор | `client`, many-to-one к Users; ID определяется сервером по Telegram |
| Начальный статус | `status = created` |

Доступные статусы таблицы: `created`, `in_progress`, `completed`, `archived`.
`Answers` при создании не заполняется. Сервер отклоняет создание и просмотр заявок
для незаполненного профиля. Автор и начальный статус не принимаются от клиента.
Повторная отправка одной формы после сетевого сбоя использует тот же ID и не создаёт дубликат.

Главная показывает открытые заявки (`created`) из БД, новые — первыми.
После публикации заявка появляется на главной и в «Моих заявках»; перезагрузка
повторно читает БД. Пустая таблица даёт пустую ленту, а ошибки загрузки показываются
с кнопкой повтора. Подстановки тестовых данных нет; старый localStorage не используется.
Список читается постранично, поэтому отображаются и записи за пределами первых 100.

В Requests нет колонок времени или места. Время можно указать в описании;
город и район показываются из профиля автора. Фильтр «Рядом» означает тот же город
и район, без вымышленных расстояний. Телефон и Telegram ID автора в ленту не передаются.
Награда, отметки, дата создания и реальный статус видны в карточке и на странице заявки.
Счётчики выполненных дел не показываются, пока не подключено завершение заявок.

## Отклики и рейтинг

Другой пользователь с заполненным профилем может откликнуться на открытую заявку.
Действие `answers.create` создаёт RequestsAnswers с двумя полями: `request` — ID
заявки, `worker` — ID исполнителя, определённый сервером по Telegram. Текст сообщения
не запрашивается: в текущей таблице для него нет колонки. Ответить на свою или
закрытую заявку нельзя. Детерминированный ID пары заявка/исполнитель защищает от
дублирования при повторных нажатиях и сетевых повторах.

| Связь | Настройка |
| --- | --- |
| `Requests.Answers` ↔ `RequestsAnswers.request` | two-way one-to-many; Requests — parent, RequestsAnswers — child |
| `RequestsAnswers.worker` | many-to-one к Users |
| `Reviews.users` | many-to-one к Users; пользователь, которому поставили оценку |
| `Reviews.rating` | double, оценка от 1 до 5 |

В текущей схеме Appwrite обе стороны двусторонней связи отображаются как
`oneToMany`, но `request` имеет `side=child` и принимает один ID, а `Answers`
имеет `side=parent` и содержит список. Обратную связь обновляет сам Appwrite;
код не заменяет список чужих откликов. Схему менять не нужно.

`answers.mine` читает из БД только отклики текущего исполнителя и связанные заявки.
Они отображаются в «Моих откликах» и остаются после перезагрузки. Если заявку удалили,
отклик помечается как относящийся к удалённой заявке.
Автор открывает «Мои заявки» → заявку и видит список исполнителей под ней:
имя, фамилию, рейтинг и число отзывов. `answers.list` доступен только автору.
Кнопки «Обновить» повторно читают БД; постоянной подписки Realtime пока нет.
Телефоны и Telegram ID исполнителей клиенту не передаются.

Рейтинг — арифметическое среднее всех числовых `Reviews.rating` от 1 до 5,
связанных через `Reviews.users`, округлённое до двух знаков. Пустые и недопустимые
оценки не учитываются. При отсутствии отзывов в `Users.Rating` записывается 0,
а интерфейс показывает «Пока нет отзывов». Расчёт читает все страницы отзывов.
Рейтинг пересчитывается и сохраняется при отправке отклика, загрузке своих
откликов и просмотре исполнителей автором. Если отзывы меняются напрямую в БД,
новый рейтинг сохранится при следующем таком запросе; фонового обработчика
событий Reviews пока нет. Формы создания отзывов этот этап не добавляет.

Для localhost уже используются ID таблиц из `.env`. Для размещённого сайта
добавьте в окружение функции `APPWRITE_REQUESTS_ANSWERS_TABLE_ID` и
`APPWRITE_REVIEWS_TABLE_ID`, затем повторно разверните обновлённый `server/profile-api/`.
Дополнительных scopes к `rows.read` / `rows.write` не требуется.
Профили, заявки и отклики не хранятся в localStorage. Чат, выбор исполнителя,
отмена отклика и изменение статусов пока не подключены.

## Проверки

```bash
npm test        # сценарии Users/Cities, валидация, Telegram, гонки и ошибки
npm run lint
npm run build
```

Автотесты используют изолированный репозиторий и не меняют реальную БД.
